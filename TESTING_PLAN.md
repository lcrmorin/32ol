# xgb2sql test hardening - status

## XGBoost -> SQL (28 tests, ~145s to run - most of it is XGBoost training)

Real bugs/gaps found and fixed:

1. **SQL injection / broken queries from unescaped category labels.** `'{v}'` with no escaping meant any category containing a quote ("O'Brien") produced broken or silently wrong SQL. Fixed with proper `''`-doubling; tested end-to-end against DuckDB.
2. **`booster="dart"` silently returned wrong predictions.** Verified empirically: summing all dumped trees gives ~0.007 vs the model's real ~0.25 prediction on a test case, because DART's dropout weighting isn't recoverable from `get_dump()`. Now raises `NotImplementedError` immediately.
3. **`booster="gblinear"`** (not a tree model) now raises immediately instead of producing nonsense from tree-shaped code.
4. **Objectives beyond binary:logistic/reg:squarederror were unsafe.** A `count:poisson` or `reg:gamma` model called with the old `sigmoid=False` default silently returned a raw margin as if it were a real prediction. Added an explicit, empirically-verified link-function table (`identity` / `logistic` / `exp`) with auto-detection from the objective, and an error for anything not verified - added real `exp`-link support (tested against `count:poisson`) rather than just blocking it.
5. **`base_score` exactly 0 or 1** (logit blows up) and **`base_score <= 0`** (log undefined for exp-link) now raise a clear error instead of a silent, wrong fallback.
6. **`num_class` mismatch** in `xgboost_to_sql_multiclass` now raises instead of silently misassigning trees to the wrong classes.
7. Confirmed **`num_parallel_tree` > 1 needs no special handling** (I expected it might need dividing - checked empirically, it doesn't). Locked in as a regression test so a future refactor can't silently break it.
8. Added the untested combination: **multiclass + categorical features together**.
9. Added an **end-to-end test for a SQL-reserved-word column name** (`select`, `order`) - previously only unit-tested against the quoting helper in isolation, not run against a real database.

Real limitation found, documented rather than "fixed" (can't be fixed generically):

10. **SQLite cannot be a target engine for this tool.** The correctness trick this module relies on - `CAST(x AS FLOAT)` to force a float32 comparison matching XGBoost's internal one - is a no-op on SQLite, which has no true 4-byte float type. Confirmed empirically: ~7% of rows get routed down the wrong branch, up to 0.43 absolute error.

**Not done yet - MySQL/PostgreSQL never verified against a real instance**, only DuckDB. Needs Docker (or a GitHub Actions workflow with `postgres:`/`mysql:` service containers) - not available in any sandbox this package has been built in.

## Architecture refactor (this session)

Split the single xgboost-specific `converter.py` into: `ir.py` (canonical tree representation - `Leaf`/`Split`/`Tree`/`Ensemble`), `parse_xgb.py` (XGBoost `Booster` -> IR), `emit_sql.py` (IR -> SQL), `emit_sas.py` (IR -> SAS). `converter.py` is now a thin backward-compatible wrapper. All 20 prediction-equivalence/guardrail xgboost tests still pass unchanged after the refactor (confirms it's behavior-preserving, not just structurally different).

The IR added two fields the original xgboost-only code didn't need, because they're real differences between model libraries, not just style: `Split.le` (xgboost's yes-branch condition is `value < threshold`; sklearn's is `value <= threshold`) and `Ensemble.threshold_precision` (`"float32"` for xgboost, which needs the CAST trick; `"float64"` for sklearn, which must NOT be truncated to float32 or it would silently disagree with the model near boundaries).

## scikit-learn -> SQL and -> SAS (22 tests, ~9s to run)

New this session. Supported: `DecisionTreeRegressor`, `DecisionTreeClassifier` (binary + multiclass), `RandomForestRegressor`, `RandomForestClassifier` (binary + multiclass), `GradientBoostingRegressor` (`loss="squared_error"` only), `GradientBoostingClassifier` (binary only, `loss="log_loss"` only). Every base-score/link-function formula below was checked empirically against the model's own `predict`/`predict_proba`/`decision_function` before being coded, not assumed from documentation:

- `DecisionTreeRegressor`/`RandomForestRegressor`: leaf value is the training-sample mean at that leaf; RF averages trees with equal weight `1/n_estimators`. No link function.
- `DecisionTreeClassifier`/`RandomForestClassifier` (any number of classes): each leaf stores training-sample class counts; the converter uses the per-class normalized proportion directly as that class's SQL/SAS output. RF's mean-of-trees is exactly `predict_proba` (verified) - no softmax needed, unlike XGBoost/GBM multiclass, because these are already valid probabilities that sum to 1 by construction.
- `GradientBoostingRegressor`: base score is `model.init_.constant_[0][0]` (the fitted `DummyRegressor`'s constant - confirmed empirically equal to `mean(y)` for `loss="squared_error"`), trees weighted by `learning_rate`, identity link. Other losses (`huber`, `quantile`, `absolute_error`) raise `NotImplementedError` - their base-score/link formulas haven't been checked.
- `GradientBoostingClassifier` (binary): base score is `logit(model.init_.class_prior_[1])`, trees weighted by `learning_rate`, logistic link. Verified against `decision_function`/`predict_proba` bit-for-bit (within float rounding). **Multiclass (a later round): implemented** - `n_classes` raw-margin trees per boosting round, softmax across classes, verified per-class against `predict_proba` (same pattern as XGBoost's existing multiclass support). The plain binary `sklearn_to_sql`/`sklearn_to_sas` entry points still reject a multiclass model with a message pointing at `sklearn_to_sql_multiclass`/`sklearn_to_sas_multiclass`.
- **Missing values**: sklearn (>=1.3) trees carry a per-node `missing_go_to_left` flag. Verified empirically - built a model with NO missing values in training, then called `.predict()` with NaN inputs and confirmed the converter's output matches exactly, both via SQL (DuckDB) and via the SAS interpreter. This is real, checked support, not an assumed fallback.
- **Guardrails tested**: unsupported model type raises; multiclass classifier rejected by the binary entry point with a clear message pointing at the multiclass one; unsupported `GradientBoosting` loss raises; SAS name-literal quoting for a column name that isn't a valid plain SAS identifier; string-literal quote-escaping (shared test against both the SQL and SAS quoting helpers).

### SAS-specific: not verified against real SAS

No SAS installation has been available anywhere this package has been built. `tests/sas_interp.py` is a hand-written interpreter for the exact SAS expression subset `emit_sas.py` emits (nested `IFN(MISSING(col), missing_branch, IFN(condition, yes_branch, no_branch))`) - it catches real bugs (wrong operator, wrong branch routing, quoting mistakes, sign errors) by evaluating the generated text against `.predict()`/`.predict_proba()`, but it shares the same author (this session) as the emitter, so a shared misunderstanding of SAS semantics would not be caught by it. Two SAS-specific quirks were deliberately designed around rather than assumed to be fine:

- SAS's `IFN`/`IFC` functions evaluate ALL of their arguments (not short-circuiting like an `IF-THEN/ELSE` statement) - per SAS's own documented behavior. This means a deep tree evaluates every branch on every call, not just the taken one. Handled correctly in the interpreter (and should be fine in real SAS, since it's documented function behavior) but not benchmarked for performance on a large ensemble.
- SAS treats a numeric missing value as smaller than any real number for ordinary comparisons (`. < 5` is TRUE) - this is NOT SQL's three-valued NULL logic. The emitter deliberately checks `MISSING(col)` explicitly first in every split, rather than relying on a comparison against a missing value to "propagate" missingness the way the SQL emitter can rely on NULL propagation. This was a design decision made BEFORE writing any code, specifically to avoid depending on that comparison quirk being exactly as remembered.

**xgboost -> SAS is blocked entirely** (raises `NotImplementedError`, tested) rather than shipped unverified - see README.md's "Why xgboost has no SAS output yet".

## HistGradientBoosting -> SQL and -> SAS (8 tests + 5 categorical tests, `tests/test_sklearn.py`)

Confirmed by directly inspecting the fitted model's raw node arrays (`predictor.nodes`, a structured numpy array) that `num_threshold` is genuine float64 (`dtype('<f8')`) - unlike plain XGBoost, HistGradientBoosting bins data for training SPEED but stores the real, un-truncated split value for inference. Verified by manually walking `nodes`/`left`/`right`/`missing_go_to_left` for every row of a real fitted model and comparing to `.predict()`/`.predict_proba()`: exact match (0.0 difference) on continuous (non-quantized) data, with and without missing values. Stored leaf `value` already has the learning rate folded in (unlike plain `GradientBoostingRegressor`, where it has to be multiplied in manually) - confirmed the same way, by not multiplying and getting an exact match.

**Categorical splits: implemented and verified (a later round; previously raised `NotImplementedError`).** HistGradientBoosting routes a categorical split via a 256-bit bitset per node (`raw_left_cat_bitsets`, `(bitset[v//32] >> (v%32)) & 1`), decoded directly - no caller-supplied value mapping needed (unlike LightGBM/CatBoost below), since the bitset already operates on the model's own known category codes. Verified end-to-end against DuckDB, including a mixed numeric+categorical model and the unseen-category-at-predict-time case.

A real, separate bug was caught while implementing this, not by inspection but by an end-to-end DuckDB test disagreeing with `.predict()`: sklearn's `HistGradientBoosting` internally reorders features (categorical columns first, then numeric, each group in original relative order) via a `ColumnTransformer` whenever a model has ANY categorical feature - so `node.feature_idx` was in this REORDERED space, not the caller's raw column order, for every split in the tree (numeric splits included, not just the categorical ones). This directly invalidated an earlier claim in this file ("verified: no reindexing needed") from before any model actually had a categorical feature - that claim was true only in the special case it happened to be tested under. Fixed via `_hgb_feature_order(model, feature_names)`, which reads `model.is_categorical_` and returns the reordered name list (or the names unchanged if there are no categorical features at all, the case the original claim was actually checked against).

Multiclass HistGradientBoostingClassifier: implemented and verified (see the LightGBM/CatBoost multiclass note below - same per-round-softmax approach, same verification method: `sklearn_to_sql_multiclass`/`sklearn_to_sas_multiclass` checked class-by-class against `predict_proba`).

## XGBoost -> SAS via quantization (6 tests, `tests/test_quantize.py`)

**The investigation that led here started as an attempt to answer: "is there a training-time trick that makes XGBoost safe for a target with no float32 cast?"** Two ideas were tested empirically rather than assumed:

1. **Round/quantize continuous features to a coarser decimal grid** (e.g. 2 decimal places) before training, hoping the wider gap between grid points would put real distance between any threshold and any achievable value. **Tested and REJECTED**: built a real XGBoost model on 0.01-grid-rounded data and checked all 916 thresholds against nearby grid points - 4780 mismatches out of 37556 checks (default `hist` method), still 1880/39360 even with `tree_method='exact'`. Some thresholds landed essentially on top of a grid point. Root cause: XGBoost's split-threshold placement (both histogram-based and exact-greedy) does not respect an arbitrary decimal grid's spacing - it can place a threshold arbitrarily close to any real candidate value, not just "at a safe midpoint between two adjacent grid points" as hoped.

2. **Quantize to a small number of ordinal INTEGER bins** (0, 1, 2, ...) instead of decimal rounding. **Tested and this works, with an important caveat.** With small bin counts and shallow trees (K<=256, depth<=6), every threshold landed at an exact half-integer (X.5) - 0 mismatches across tens of thousands of checks, both `hist` and `exact` tree methods. This makes sense: with only integer inputs, the natural "midpoint of two adjacent distinct values" split point IS a half-integer, and no float32 rounding noise (~1e-7 relative) can push a half-integer threshold within reach of an integer 0.5 away.

   This is necessary but was initially thought to be sufficient - it isn't, on its own, guaranteed for every bin count and depth (see the checker correction below), which is why `xgboost_to_sas` does not just trust "you quantized to integers" - it verifies the SPECIFIC trained model, every time.

### The safety checker had a real bug, caught before shipping

First version of `check_xgb_sas_safety` used a distance heuristic: "flag a threshold if it's closer than N x (float32 danger band) to the nearest achievable integer." This is backwards for the exact-coincidence case - a threshold sitting exactly ON an achievable value (margin = 0) is the SAFEST case (comparing a value to itself is deterministic in any precision), not the worst one. Running this heuristic against a model with 1000 bins and `max_depth=8` produced 2597 "violations", all of the form "threshold 5.0 is only 0 from achievable value 5."

Rewrote the checker to directly SIMULATE the actual comparison (`float64(v) < threshold` vs `float32(v) < float32(threshold)`) for every achievable integer within a small window of each threshold, instead of using a distance proxy. Re-ran against the same 1000-bin/depth-8 model: **0 violations** - it was safe all along, confirmed end-to-end by generating SAS from it and checking it against `Booster.predict()` (max diff ~5.7e-8, consistent with ordinary float32 threshold-rounding noise, not a bug). `tests/test_quantize.py::test_synthetic_unsafe_threshold_is_caught` hand-constructs a threshold placed exactly in the float32 danger band (`5.0 + 1e-7`, which rounds down to exactly `float32(5.0)`) to prove the checker still catches a REAL disagreement when one exists, not just that it accepts everything now.

**Practical upshot for the "how do I get XGBoost to SAS" question**: `xgb2sql.IntegerBinner` + `xgb2sql.xgboost_to_sas(model, bins_per_feature=binner.levels())` is a real, tested path - but `HistGradientBoostingRegressor`/`Classifier` is simpler and doesn't need any of this (no quantization, no verification gate, just works) if XGBoost specifically isn't a hard requirement.

## LightGBM -> SQL and -> SAS (20 tests, `tests/test_lgbm.py`)

Investigated before any code was written, the same way every other precision question in this project has been: does LightGBM compare split thresholds in float64 (like sklearn) or truncate to float32 (like xgboost)? Built a real model, walked its `dump_model()` tree two ways (plain float64 comparison, and an xgboost-style float32-cast comparison) against `Booster.predict()`, then constructed adversarial rows placed exactly in the float32-rounding danger band (a value that is float64-greater than a threshold but rounds down to the threshold's own float32 value). Result: the float64 walk matched `predict()` exactly (0.0 diff) including on the adversarial rows; the float32-cast walk was off by up to 0.49 on those same rows. **LightGBM is float64-native, like sklearn - not float32-truncated, like xgboost.** This was the single most consequential finding of this round: it means `lgbm_to_sas` needs no quantizer, no safety check, and no accuracy tradeoff - it "just works" through the same code path as `sklearn_to_sas`.

Other things verified before writing `parse_lgbm.py`:

- **Missing-value routing** uses each split's own `default_left` flag (same shape as sklearn's `missing_go_to_left`). Verified this holds even for a split whose training data never included a NaN at all (`missing_type: "None"` in the dump) - fed an out-of-training-distribution NaN at predict time and confirmed `default_left` still governs it correctly (0.0 diff), not just when the dump's `missing_type` says `"NaN"`.
- **Learning rate and `boost_from_average` bias are already folded into the dumped `leaf_value`.** Verified by summing raw leaf values with no extra scaling and matching `Booster.predict(raw_score=True)` exactly, for a regression model with a large constant offset added to `y` specifically to make a missed bias term obvious (it wasn't missed - 0.0 diff). This means every `Tree` uses `weight=1.0` and `Ensemble.base_score=0.0` unconditionally for LightGBM - simpler than xgboost, which needs the base_score-to-margin inversion.
- **`boosting_type="gbdt"`, `"dart"`, `"rf"`, and `"goss"` are ALL supported** (a later round closed this out). The prior round's "quick check suggested `dart` might sum cleanly too" was followed up with real verification: adversarial rows (varying `drop_rate`/`max_drop` for dart, `top_rate`/`other_rate` for goss, bagging/feature fraction for rf, with and without missing values) got 0.0 diff against `.predict()` for dart/goss/gbdt via a plain leaf-value sum - LightGBM bakes any dart/goss rescaling into the stored leaf values itself, unlike xgboost's DART which is provably NOT recoverable this way (see the XGBoost section above). `rf` is a genuine, real exception: `raw_score=True` always returns the plain sum by definition regardless of boosting_type, so that first check was checking the wrong thing for rf specifically - comparing against `predict()` (probability space, what every other parser in this project actually targets) revealed rf needs the trees AVERAGED (`weight = 1/n_trees`), not summed. Fixed and locked in as a regression test for both regression and binary-classification rf models.
- **Categorical splits** (`decision_type: "=="` in the dump, where `threshold` is a `"||"`-joined string of category codes rather than a number) **implemented and verified** (a later round; previously raised `NotImplementedError`). Two distinct cases: a plain int/numeric-dtype categorical column needs no decoding (the codes in `threshold` ARE the raw values); a pandas `Categorical`-dtype column needs decoding via the model's own `pandas_categorical` list, matched to the caller-supplied `categorical_feature_values` by VALUE-SET equality rather than position (multiple pandas-categorical columns have no positional guarantee - matching by position would silently mismatch columns whenever the caller's dict key order didn't happen to match LightGBM's internal storage order). Verified via LightGBM's own C++ source (`tree.h`'s `CategoricalDecision`) that missing/unseen categories ALWAYS route to "no-match" unconditionally - `default_left` is never consulted for categorical splits, unlike numeric ones where it governs missing routing. Also confirmed (by inspecting the same source) that no float32/float64 precision question applies to categorical splits at all - it's an exact integer comparison, not a threshold comparison, so the earlier float64-native finding for numeric splits doesn't even need to be re-asked here.
- **Multiclass** (`num_class > 1`) **implemented and verified** (a later round; previously raised `NotImplementedError`) - a per-round softmax across `n_classes` trees, same pattern as HistGradientBoostingClassifier/GradientBoostingClassifier above, verified per-class against `predict_proba`.

Test coverage includes the adversarial-float32-band test as a locked-in regression test (`test_adversarial_float32_rounding_band_matches_float64`), missing-value tests (both trained-with-NaN and unseen-at-train-time-NaN), the rf-averaging regression test, both categorical cases (plain-int and pandas-dtype, including category-order-independence and unseen-category-at-predict-time), and the multiclass softmax test.

## CatBoost -> SQL, and -> SAS via the same quantizer as XGBoost (18 tests, `tests/test_catboost.py`)

CatBoost's default tree structure (`grow_policy="SymmetricTree"`) is genuinely different from every other library here: an *oblivious* tree, where every node at a given depth level shares the same split condition. A depth-`d` tree is stored as just `d` splits plus `2**d` leaf values, not a conventional per-node binary tree - so before writing any parser, the actual leaf-indexing scheme had to be reverse-engineered rather than guessed. Brute-forced all 4 combinations of (which split is the least-significant bit of the leaf index, which comparison direction sets that bit) against a real model's own `.predict()`: only one combination reproduced it exactly (0.0 diff) - `splits[0]` is the least-significant bit, and `value > border` (not `>=`) is the direction that sets a bit to 1. The other three combinations were off by tens of units. `parse_catboost.py` reconstructs an equivalent conventional binary tree (`2**depth - 1` internal nodes) from this compact form so it fits the shared IR.

**Precision - the one finding here that ran against the "modern gradient booster, probably like LightGBM" assumption**: CatBoost's stored split borders are float32 values (every border checked in a real model's JSON dump was bit-identical to its own float32 rounding) - so far, similar to xgboost. What actually matters, though, is whether the *incoming* feature value also gets truncated to float32 before comparison, the same way it's checked for every other library here: built adversarial rows in the float32-rounding danger band and compared against real `.predict()`. Result: 0.0 diff against the float32-cast-truncated manual walk, and a diff of ~48 (on a toy model) against a plain float64 walk. **CatBoost needs the exact same treatment as xgboost** - `threshold_precision="float32"`, the SQL `CAST(col AS FLOAT)` trick, and the same IntegerBinner-quantize-then-verify gate (not a free pass) to reach SAS. `catboost_to_sas` reuses `check_xgb_sas_safety` as-is (it's generic over any float32-precision `Ensemble`, not actually xgboost-specific in its implementation) rather than duplicating it.

Other things verified before/while writing `parse_catboost.py`:

- **Missing values are a per-FEATURE, not per-split, property** (`nan_value_treatment` in the model dump: `"AsTrue"`, `"AsFalse"`, or `"AsIs"`) - a single flag applies to every split on that feature throughout the whole model, unlike xgboost/LightGBM/sklearn's per-node missing branch. Verified `"AsTrue"` routes NaN like `bit=1` and both `"AsFalse"`/`"AsIs"` route it like `bit=0`, including the unseen-at-train-time case (a feature with no NaN at train, `"AsIs"`, still gets fed a NaN at predict time in one test - CatBoost's own `.predict()` silently accepts it and routes it like `bit=0`, confirmed 0.0 diff against a manual walk assuming exactly that).
- **The base score (`scale_and_bias` in the model dump) applies once across the WHOLE ensemble**, not per-tree like `GradientBoostingRegressor`'s `learning_rate` - `prediction = bias + scale * sum(every tree's leaf value)`. Folded into the IR by giving every `Tree` the same `weight=scale` and the `Ensemble` `base_score=bias`.
- **Categorical features** (`cat_features=[...]` at training) - **partially implemented (a later round)**. CatBoost resolves a categorical feature one of two structurally different ways depending on cardinality relative to `one_hot_max_size`: a plain `OneHotFeature` split (low cardinality) or an `OnlineCtr` split (order-dependent, permutation-based target-statistic counter - high cardinality). `OneHotFeature` is fully implemented and verified: the category-to-hash mapping is resolved by calling CatBoost's own `format="CPP"` model exporter against a minimal synthetic `Pool` and regex-extracting its `CatFeatureHashes` static table - deliberately using CatBoost's own official exporter as an oracle rather than reimplementing CatBoost's hash function, which would be one more place to get subtly wrong. `OnlineCtr` is NOT implemented - its `CalcHash` 64-bit multiplicative hash (`MAGIC_MULT = 0x4906ba494954cb65ull`) was located in CatBoost's C++ source, but porting the per-CTR bucket-table logic on top of it was scoped as future work, not built; `_check_supported` raises `NotImplementedError` naming `OnlineCtr` specifically (gated on which split types the fitted trees ACTUALLY use, not merely whether `cat_features` was declared - a model that declares a categorical feature but never ends up splitting on it, e.g. because the target is independent of it, needs neither code path and correctly needs no `cat_feature_values` either).
  - One real bug caught during this: an early version of the split-type check looked for `"CtrFeature"` (the name CatBoost's own CPP-exporter C++ enum uses) but the model's JSON dump actually names the field `"OnlineCtr"` - a genuine CTR-using model fell through the check and crashed later with a `KeyError` inside tree-building instead of raising the intended clear message. Fixed by matching the JSON dump's actual field name.
- **`grow_policy` other than `"SymmetricTree"`** (`"Lossguide"`, `"Depthwise"`) raises - those produce a different, non-oblivious JSON structure this parser doesn't read (confirmed: the dump doesn't even have an `oblivious_trees` key for those modes).
- **Multiclass implemented and verified (a later round; previously raised)** - same per-round-softmax pattern as the other libraries, verified per-class against `predict_proba`; the quantized-to-SAS path was re-verified for multiclass too, since CatBoost's float32 truncation doesn't go away just because there are more than 2 classes.

Test coverage locks in the adversarial-float32-band test, the two NaN-treatment cases (`AsTrue` via `nan_mode="Max"`, and unseen-at-train `AsIs`), guardrails for `OnlineCtr`/Lossguide, the `OneHotFeature` success path (including the "declared but unused" edge case, and binary/multiclass together), multiclass SQL and quantized-SAS, and the full quantized-to-SAS path (`test_catboost_to_sas_matches_predict_when_safe`) mirroring the xgboost quantizer tests exactly.

## Bottom line

Two axes were added in the sklearn+SAS session (scikit-learn as a second source model, SAS as a second target language). A later round added the two remaining source models named in the project's stated goal - LightGBM and CatBoost - plus the operational deployment guidance in `DEPLOYMENT.md`. LightGBM turned out to be the "easy" case: float64-native like sklearn, so SAS output needed no quantizer at all, a genuinely good outcome verified rather than assumed. CatBoost was the opposite of easy on two independent axes at once - its oblivious/symmetric tree encoding had to be reverse-engineered from scratch (4 hypotheses tested against real `.predict()`, only 1 matched), and its precision behavior turned out to need xgboost's full quantizer treatment despite CatBoost being, like LightGBM, a "modern" gradient booster - the kind of assumption ("probably behaves like LightGBM since both are newer than xgboost") this project's verify-before-shipping discipline exists specifically to catch.

The most recent round closed out nearly every remaining gap from that point: categorical-split support for HistGradientBoosting (catching a real feature-reordering bug along the way) and LightGBM (resolving a genuine value-matching ambiguity for pandas-categorical columns), CatBoost's `OneHotFeature` categorical splits (via CatBoost's own model exporter as an oracle, never reimplementing its hash function - `OnlineCtr` remains the one open categorical case), LightGBM's `dart`/`rf`/`goss` boosting modes (with `rf` turning out to be a real, caught exception needing averaging rather than summing), and a genuine per-round softmax multiclass implementation for `GradientBoostingClassifier`/`HistGradientBoostingClassifier`/LightGBM/CatBoost - plus moving each ML library from a hard dependency to an optional extra so the package is installable with only the libraries actually needed.

Everything here is either verified against a real execution engine/model (DuckDB for SQL; direct simulation against float32/float64 arithmetic and against `.predict()`/`predict_proba()` for quantizers, categorical routing, and multiclass softmax alike) or explicitly and prominently marked as unverified (SAS-against-real-SAS, and the still-open Postgres/MySQL gap) - nothing is silently assumed to work, and multiple cases across the project's history (decimal-grid quantization for xgboost, "maybe CatBoost is float64-native like LightGBM", and an earlier "no reindexing needed" claim for HistGradientBoosting that held only in the absence of any categorical feature) were explicitly tested and either rejected or corrected rather than left as untested "should work" claims.
